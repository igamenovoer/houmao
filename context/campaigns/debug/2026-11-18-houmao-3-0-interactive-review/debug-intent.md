## Problem Statement

The current qualification target is Houmao `3.0.0rc3` (tag `v3.0.0rc3`, commit `4f3ba508`). RC3 adds four managed run modes (`headless`, `service`, `tui`, and `web`), native DSH one-shot headless execution, persistent DSH ACP service, Kimi ACP service and Web, Codex app-server service, and unified owner-bound manager/gateway control. It replaces `--headless` and `--no-headless` with `--mode` and introduces new launch-plan, session-manifest, registry, and execution-locator schemas. These changes invalidate the original DSH arm definitions and command examples, not merely the release number.

The campaign originally targeted `3.0.0rc1` (tagged at `f99ce02c`, with `devel` at `6207d279`) and its seven major capabilities over `v2.4.0`: authenticated gateway access (`#84`), execution-owner-aware launch and control (`#81`), DeepSeek Harness `dsh_acp` and `dsh_web` backends (`#74`), native agent home inspection and common-plugin refresh (`#82`), the gateway plugin SDK (`#76`) with `houmao-cccc` chat and deferred Mail (`#77`, `#78`), explicit dual mailbox bindings with bounded Stalwart synchronization (`#79`, `#80`), and durable agent usage records (`#83`). Those areas remain in scope, but their current RC3 contracts and mode-specific behavior are the relevant test targets.

Automated passes establish internal protocol compliance, yet they do not show what an operator experiences when driving these features step by step in real time. The campaign evaluates each capability under live human observation so the reviewer can watch agent execution directly in isolated tmux sessions, browser views, service dashboards, and CLI or HTTP responses, then judge whether each feature works cleanly or requires code, CLI, UX, or documentation revision before `3.0.0` final. RC1 and RC2 observations remain evidence for those releases only and must be rerun when the RC3 contract differs.

## Scope and Implementation Boundary

- **In scope**: Human-watched interactive walkthroughs executed via the maintained launch fixture and reusable campaign helpers in [scripts/explore/houmao-3-0-interactive-review/](../../../../scripts/explore/houmao-3-0-interactive-review/). Each iteration uses fresh release-specific roots. For RC3, all generated inputs and fixture runs are stored physically under the Git-ignored `tmp/houmao-30-iter2-rc3/` directory, including private `assets`, `home`, `workdir`, gateway access state, and `run.json`. An explicitly operator-approved support change permits purpose-specific checkout `tmp/` run roots in the fixture and gateway storage policies; other checkout locations remain rejected. Every run uses an explicit isolated `-L` or `-S` tmux server and exact attach details, with browser UIs, CCCC Web UI, Stalwart logs, gateway HTTP traffic, and CLI outputs as applicable. Every step pauses at human review checkpoints before advancing. Historical RC1/RC2 roots and manifests are evidence, not reusable RC3 runtime state.
- **Read-only assets**: Production source code under `src/houmao/` and `packages/houmao-cccc/`, committed tests under `tests/`, OpenSpec specifications under `openspec/`, active user tmux sessions (`mao-1..4`, `rsi-1..4`) on the default server, and secret credential files remain untouched during diagnostic execution. The sole exception is the separately and explicitly operator-requested 2026-11-19 fixture/gateway checkout-`tmp` storage-policy fix with its focused tests and documentation.
- **Out of scope**: Postponed Pi backend (`#75`), live Docker container execution (no Docker daemon or socket is present in this environment per [execution README](../../../../tests/integration/execution/README.md)), physical multi-host networking across separate machines, and direct product code edits during diagnostic runs.

## Success Criteria

- Interactive execution protocols and live watch procedures (tmux attach targets, browser URLs, log tails, and pause checkpoints) are defined and run for the prioritized feature arms against the current RC3 contracts.
- Each tested feature arm receives an evidence-backed review disposition: **Works as designed**, **Works with caveats or UX friction**, or **Needs revision**.
- Observed issues, confusing CLI or browser ergonomics, unclear error messages, observability gaps, and documentation mismatches are captured with exact commands and outputs in `evidences/`, analyzed in `discussions/`, and synthesized into prioritized revision candidates in `reports/`.

## No-Product-Change Declaration

This campaign is an isolated interactive diagnostic and review effort. Temporary campaign helpers, tmux isolation wrappers, and interactive step runners live strictly under [scripts/explore/houmao-3-0-interactive-review/](../../../../scripts/explore/houmao-3-0-interactive-review/). Diagnostic runs do not authorize modifying production code under `src/houmao/` or `packages/houmao-cccc/`, modifying existing tests under `tests/`, or editing OpenSpec specifications. The checkout-`tmp` storage-policy fix on 2026-11-19 was separately and explicitly requested by the operator and is documented in [its implementation log](logs/2026-11-19-checkout-tmp-storage-policy-fix.md). The experiment was validated, then reverted at operator direction; the finding and live proof are documented in the [registry-permission log](logs/2026-11-19-h1-live-hello-and-registry-permission-denial.md), and the proposed product fix is [issue #86](https://github.com/igamenovoer/houmao/issues/86).
