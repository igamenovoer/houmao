## Product Usability Findings

These findings describe agent and driver ergonomics during an otherwise passing run. They did not change any scenario verdict.

Tracking: [GitHub issue #99](https://github.com/igamenovoer/houmao/issues/99).

### CCCC CLI Endpoint Semantics and Opaque Validation Failure

- **Observed**: both real agents needed several attempts to discover the supported CLI command shapes. Agent A tried unsupported forms including `binding get`, `--json`, `--recipient`, and `--message` before sending successfully. Agent B first tried `--local-plugin-url`, then supplied the advertised `local_plugin_url`, including `/v1/plugins/cccc`, as `--gateway-url`. Binding, capabilities, and reply attempts with that URL returned only `{"error_code": "cccc_cli_failed"}`.
- **Why it happened**: the incoming CCCC envelope advertises a full local plugin route for direct HTTP, while `houmao-cccc --gateway-url` requires the gateway origin and appends `/v1/plugins/<instance>` itself. In a managed generation, `managed_self_gateway_client` also requires an exact match with the current owner endpoint. The longer plugin URL fails that selection, and the CLI's broad `ValueError` handling collapses the actionable cause into `cccc_cli_failed`.
- **Workaround**: agent B used the documented direct `POST /v1/plugins/cccc/chat/reply` route, which returned HTTP 200 and produced the one expected threaded reply. The test role now explicitly permits that local HTTP alternative. The test helper passes only the gateway origin to `--gateway-url`.
- **Product opportunity**: reject a plugin-route URL with an actionable message that shows the expected origin form, or accept and normalize it deliberately. Include an exact CLI reply example alongside `local_plugin_url` in the incoming hint. The existing generic error avoids leaking details, but it should still distinguish an invalid endpoint from unavailable managed-self authority.

### Cross-Surface Readiness Discovery

- **Observed**: the initial Doctor required top-level `host_process_alive` and `/v1/control/headless/state` for DSH Web, so it stopped before the first prompt even though both Web agents were usable.
- **Why it happened**: DSH Web exposes `availability`, `host_process_alive`, and `can_accept_prompt_now` under `web` in `/v1/status`, with `native_surface_eligibility` at the top level. Headless readiness instead uses `/v1/control/headless/state`. A driver written for headless cannot reuse the same field paths without a surface-specific branch.
- **Workaround**: `live_observation()` now reads the nested Web fields when `web` is present and otherwise uses the headless route. Doctor checks those normalized fields together with gateway health and native-surface eligibility.
- **Product opportunity**: document one canonical cross-surface readiness recipe for automation, or expose a common normalized readiness summary. This is a discovery problem, not incorrect Web readiness behavior.

### Delivery Receipt Ordering Is Easy to Misread

- **Observed**: after the busy refusal and explicit retry, `chat deliveries` returned `accepted` before `refused`. The actual chronology was `refused,accepted`. The response contains attempt IDs and states but no attempt timestamps or explicit ordering field.
- **Why it happened**: CCCC presents persisted receipts newest-first, while the helper initially treated array order as chronology. This caused a false final-verification failure despite correct product behavior.
- **Workaround**: the helper reverses the receipt array before comparing chronological expectations. Native transcripts and the no-replay checkpoints independently confirmed the actual order.
- **Product opportunity**: document newest-first ordering next to the `chat deliveries` command and response contract. Consider an explicit ordering field, a chronological option, or attempt timestamps so clients do not need out-of-band knowledge.

### CCCC Installation Documentation Has Stale Version Contracts

- **Observed**: `docs/reference/gateway/cccc.md` says the distribution uses gateway SDK version 1 and supports Houmao `>=2.4,<3`.
- **Why it happened**: the current package declares SDK version 2 in `packages/houmao-cccc/src/houmao_cccc/__init__.py` and `packages/houmao-cccc/README.md`, while `packages/houmao-cccc/pyproject.toml` requires Houmao `>=3.0.0rc1,<4`. The reference document was not updated with the current package contracts.
- **Workaround**: the run used the installed package metadata, current package README, CLI help, and implementation rather than the stale installation/version statements.
- **Product opportunity**: update the reference document's SDK and Houmao version statements and add a documentation check or release step that keeps them aligned with package metadata.

The initial missing offline-mailbox initialization remains a harness omission, not a product usability issue. The patched external-receiver provider and checkout-external credential placement were documented prerequisites, so they are not reported as product defects.
